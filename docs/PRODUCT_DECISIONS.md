# PRODUCT DECISIONS — 탄생 마켓플레이스

> 마스터 명세서(`TANSAENG_MARKETPLACE_CLAUDE_CODE_MASTER.md`) 1.3/20장 기준으로,
> M0 구현 과정에서 실제로 선택한 기본값과 그 이유를 기록한다. 법적/세무/계약 판단은 포함하지 않는다.

## 확정 사항 (마스터 문서 그대로 적용)

- 브랜드명 "탄생 / TANSAENG", 웹+PWA, 로컬 선개발.
- 기존 환경제어·운영 홈페이지와 완전 분리.
- 직접판매형(`DIRECT_SALE_ENABLED`) 기본 `false`.
- 실PG/실SMS/실카카오/실푸시 전부 Mock, 기본 비활성.

## M0에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| Next.js 16(App Router) + Tailwind CSS 4 + TypeScript strict 채택 | 마스터 문서 12.1 권장안과 일치, 생성 시점 기준 안정 최신 버전 |
| `next.config.ts`의 `cacheComponents`/`partialPrefetching` 비활성화 | 이 신규 버전의 기본 템플릿이 활성화하는 실험적 정적 우선 캐싱 모델이 `usePathname()` 등 런타임 훅과 충돌해 빌드 실패 발생. 마켓플레이스는 장바구니·주문·관리자 등 대부분 사용자별 동적 렌더링이 필요해 M0에서는 끄는 것이 안전. M1 이후 SEO가 중요한 공개 상품/카테고리 목록에 한해 `"use cache"`와 함께 선택적 재도입 검토 |
| IA(정보구조) 라우트를 공용 `PlaceholderSection` 컴포넌트로 일괄 생성 | 40개 이상의 라우트 뼈대를 각각 손으로 작성하면 중복이 커짐. 실제 기능은 M1부터 개별 구현 |
| M0 단계에서 실제 PostgreSQL/Prisma 연결 보류 | 마스터 문서 17장 M0 범위는 "안전한 프로젝트 기반"이며 DB/스토리지는 M1에서 본격 도입. 이 머신에 PostgreSQL이 아직 설치되어 있지 않아(§SAFETY_BASELINE §3) 설치 여부를 M1 착수 시 사용자에게 먼저 확인 |
| `node_modules`를 프로젝트 폴더(Windows 드라이브, `/mnt/d/...`)에 두지 않고 로컬 검증은 별도 네이티브 경로에서 수행 | WSL에서 Windows 드라이브(drvfs)로 수만 개의 작은 파일을 쓰는 `npm install`이 비정상적으로 느림(실측: 네이티브 8~9초 vs drvfs에서 10분 이상 진행 중 중단). `node_modules`는 원래 Git에도 커밋되지 않는 산출물이므로, 실제 개발 시 Windows 네이티브 Node 또는 WSL 네이티브 경로에서 `npm install`을 직접 실행하도록 README에 안내 |

## M1에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| DB를 사용자 선택에 따라 **SQLite로 우선 구현** (M2 진입 전 PostgreSQL 전환 예정) | 로컬 PostgreSQL 설치에 `sudo` 비밀번호가 필요해 에이전트가 직접 실행할 수 없었음. 사용자에게 (1)SQLite 우선 (2)직접 sudo 실행 (3)Docker 활성화 중 선택지를 제시했고 SQLite를 선택받음 |
| NextAuth(Auth.js) 대신 **커스텀 세션(bcryptjs+jose+httpOnly 쿠키)** 채택 | 이 프로젝트는 Next.js 16(매우 최신, 베타 성격의 Cache Components 등 포함)을 사용 중이라 NextAuth v5(beta)와의 호환성 리스크가 있다고 판단. 표준 OWASP 권장 요소(단방향 해시, 서명된 세션, HttpOnly/SameSite 쿠키)는 그대로 충족 |
| `next.config.ts`의 `cacheComponents`/`partialPrefetching` 비활성 유지(M0 결정 유지) | M1에서도 로그인 세션·장바구니 등 사용자별 동적 렌더링이 대부분이라 여전히 불필요 |
| `middleware.ts` → **`proxy.ts`로 전환** | Next.js 16.4.1 빌드 시 "middleware 컨벤션은 deprecated, proxy로 이름 변경됨" 경고 발생. 공식 마이그레이션 가이드대로 파일명/함수명만 변경(`middleware` → `proxy`), 동작은 동일 |
| `next dev`/`next start`에 **`-H 127.0.0.1` 명시** | `-H` 생략 시 Node 기본 동작으로 `0.0.0.0`(모든 인터페이스)에 바인딩됨을 실측으로 발견(`docs/SAFETY_BASELINE.md` §6-A). 안전기준 위반 가능성을 코드로 고정해 방지 |
| 판매자 승인 전 상품은 `DRAFT`, 승인 후 상품은 `ON_SALE`로 자동 분기 | 마스터 문서 2장의 "판매자(심사대기): 판매 게시 불가, 초안 가능" 요건을 코드로 구현. 승인 시점에 기존 DRAFT 상품도 일괄 `ON_SALE`로 전환 |
| 상품 사진/영상 업로드는 **M1 범위에서 제외** | M1 체크리스트가 넓어 핵심 거래 흐름(인증/카테고리/찜/입점심사)을 먼저 완성하고 검증하는 것을 우선함. 상세페이지는 "사진 없음" 플레이스홀더로 정직하게 표시 |
| `vitest`를 `^3`→`^4`로 업그레이드 | `npm audit`에서 `tinypool`의 치명적(critical) 프로토타입 오염 취약점 발견, 비파괴적 해결책이 메이저 업그레이드뿐이었음. 테스트 전용 devDependency라 런타임 영향 없음 확인 후 적용 |
| `eslint-config-next`의 `fast-glob` 체인, `prisma`의 `deepmerge-ts` 고위험 취약점은 **수용(accept)** | 둘 다 빌드/린트 전용 도구 체인이며 공개 인터넷에 노출되지 않는 로컬 개발 환경 한정. 수정하려면 Next 버전과 안 맞는 `eslint-config-next@14`로 강제 다운그레이드해야 해서 더 큰 위험(버전 불일치)을 감수해야 함 |

| 결정 | 이유 |
|---|---|
| 배송지는 Order에 **스냅샷 필드**(recipientName/Phone/addressLine)로 저장, 별도 재사용 가능한 Address 테이블 없음 | M2 범위를 핵심 거래 흐름(장바구니→주문→Mock결제)에 집중하기 위한 의도적 단순화. 배송지 북마크/기본 배송지 관리는 후속 단계 |

| 주문 취소 시 Payment 상태: 결제 전이었으면 `FAILED`, 결제 확인 후였으면 `REFUNDED` | 실제 환불 프로세스(PG 연동) 없이도 상태 이력을 의미있게 구분하기 위함 |

## M2 공동구매에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 별도 스케줄러/크론 없이, 화면 표시 단계(티저/오픈/마감)를 **요청마다 현재 시각으로 계산** | "초기엔 과도한 인프라 도입 지양"(마스터 문서 12.1) 원칙. 실제 DB 상태 전이(성사/미성사)는 관리자의 수동 "마감 처리" 액션으로만 일어나며, 이는 실서비스에서도 정산 담당자가 확인 후 확정하는 흐름과 자연스럽게 맞음 |
| 공동구매 참여는 **기존 장바구니/체크아웃과 별개의 간편 참여 플로우**(수량만 입력 → 즉시 주문 생성) | 공동구매는 보통 단일 상품 집중 구매라 장바구니에 섞기보다 독립 플로우가 실제 서비스 UX에도 더 가깝고 구현도 단순함. 배송지는 임시값으로 생성되고(M2 샌드박스 단순화), 추후 체크아웃 단계 합류 여부는 M3에서 재검토 |
| 가격 단계(tiers, "0~N 미성사/N 이상 1단계")는 **미구현**, 단일 확정가만 지원 | 마스터 문서 7.2가 이를 "선택" 사항으로 명시. 상태기계/환불/동시성처럼 필수 요건을 먼저 안정화하는 것을 우선함 |
| 목표 달성 집계는 **Payment.status=CONFIRMED인 주문만** 카운트, maxQty 초과 방지는 **취소 안 된 모든 주문**(결제대기+완료) 기준 | 마스터 문서 7.2 "실제 유효 결제 주문 수량"을 그대로 따름. 다만 초과판매 방지는 결제 대기 중에도 자리를 잠가야 하므로 더 넓은 기준(committedQty)을 사용 — 두 기준을 분리한 것이 핵심 설계 포인트 |
| 공동구매 재고는 **Product.stockQty와 별도**(maxQty로 독립 관리), 일반구매 재고를 차감하지 않음 | 공동구매와 일반판매가 같은 상품의 서로 다른 "채널"로 동시에 존재할 수 있다고 가정(마스터 문서 7.1 "출하예정은 공동구매 없이 일반판매 오픈 예정 상품에도 적용 가능"과 일관) |

## 상품 미디어 업로드에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 별도 객체 스토리지(MinIO 등) 대신 **Next.js `/public/uploads/` 로컬 정적 서빙** | 로컬 개발 단계에서 가장 단순하고 즉시 동작하는 방식. `docs/ARCHITECTURE.md` 외부 서비스 경계표에 전환 계획 기록 |
| 확장자/Content-Type이 아니라 **파일 앞부분 바이트(매직 넘버)로 실제 포맷 판별** | 클라이언트가 보내는 확장자/MIME 타입은 조작 가능. HTML/SVG를 위장해 올리는 것을 `src/server/media/validate.ts`가 원천 차단(마스터 문서 8.1 요건) |
| 업로드된 사진은 **무조건 `sharp`로 재인코딩**(리사이즈+JPEG 변환), 원본 그대로 저장하지 않음 | 재인코딩 과정에서 EXIF 등 메타데이터가 자동으로 제거됨(`withMetadata()`를 호출하지 않으면 sharp 기본 동작). 별도의 "메타데이터 제거" 단계를 만들 필요가 없어짐 |
| 영상은 재인코딩하지 않고 매직바이트 검증 후 그대로 저장, 60초 길이 제한은 **미검증** | 영상 길이 확인에는 ffprobe 등 추가 바이너리가 필요해 범위를 넘어선다고 판단. 용량 제한(80MB)으로만 1차 방어 |

## 배송상태/리뷰/PWA에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| Suborder 상태는 **판매자가 한 단계씩 전진만 가능**(역행·건너뛰기 불가), 결제(`Order.status=PAID`) 전에는 전이 버튼 자체를 노출하지 않음 | 상태 일관성을 단순한 코드로 보장. 송장번호 입력 등 실제 배송 연동은 범위 밖이므로 상태 라벨만으로 충분하다고 판단 |
| 리뷰 작성 자격은 **Suborder.status=COMPLETED**(배송완료)로 한정, `Order.status=PAID`만으로는 부족 | 마스터 문서 9.4 "실제 구매 완료 주문과 연결"을 엄격히 해석. 결제만 하고 아직 받지 않은 상품에 리뷰를 못 쓰게 막음 |
| 서비스 워커는 **페이지 이동(navigate) 요청의 오프라인 폴백만** 담당, API/정적자산/개인화 데이터는 전혀 가로채지 않음 | 마스터 문서 15.1 "로그인, 개인주문, 결제, 관리자... 캐싱 금지" 요건을 가장 보수적으로 만족. Turbopack 개발 서버의 HMR과 충돌할 위험도 최소화 |
| PWA 아이콘은 텍스트 없는 **추상 도형**(원+잎 모양)으로 생성 | 이 샌드박스 환경에 한글(CJK) 폰트가 없어 SVG에 한글 텍스트를 넣으면 래스터화 시 깨짐을 사전 확인(M0 스크린샷 검증 때와 동일 이슈). 실제 로고/브랜드 아이콘으로 교체는 추후 디자인 확정 후 진행 |

## 광고(Ads)에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 광고는 **위치(placement)당 1건만 선별 노출**(여러 활성 광고 중 최신 1건), 별도 경매/입찰 로직 없음 | M3 범위에서는 "광고임을 명확히 표시"가 핵심 요건(마스터 문서 11장)이고, 복수 슬롯 로테이션/경매는 과도한 범위. 최신 승인 광고 1건만 보여주는 가장 단순한 구현 선택 |
| 검색 스폰서 광고는 **검색어와 무관하게** 노출(질의-상품 매칭 없음) | 완전한 광고 랭킹 엔진은 범위 밖. 다만 "광고" 라벨은 항상 명확히 표시해 검색 품질을 왜곡한다는 오해를 방지 |
| 광고 노출수(impressions)는 **활성 광고를 실제로 조회할 때마다** 서버에서 1 증가 | 클라이언트 측 트래킹 스크립트 없이 서버 렌더링 시점에 정확히 1회 집계. 모의 지표라 완벽한 유니크 방문자 집계는 아님을 문서에 명시 |
| 광고 클릭은 **별도 Route Handler**(`/api/ads/[id]/click`)로 리다이렉트 방식 집계 | 서버 액션은 `<form>` 기반이라 단순 링크 클릭에는 적합하지 않음. GET 리다이렉트가 표준적인 광고 클릭 추적 패턴 |

## 문의/분쟁 티켓(Support Ticket)에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 상품질문·주문문의·분쟁 3종을 **하나의 `SupportTicket` 모델 + 공통 상태기계**(`OPEN`→`ANSWERED`→`CLOSED`)로 통합 | 세 종류 모두 "구매자가 묻고 판매자/관리자가 답한다"는 동일한 1:1 스레드 패턴이라 모델을 분리할 이유가 없음. 카테고리 필드로만 구분해 화면/문구만 다르게 표시 |
| 주문문의/분쟁은 **주문(Order) 단위가 아니라 주문 품목(OrderItem) 단위로 접수**하도록 강제 | 하나의 Order가 여러 판매자(Suborder)로 분리될 수 있어, Order 단위로만 받으면 어느 판매자에게 배정할지 모호해짐. 품목을 선택하게 해 그 품목이 속한 `Suborder.sellerId`로 자동 배정 |
| 상품질문 작성 진입점은 **상품 상세페이지의 "판매자에게 문의하기" 링크로만** 제공(`/help`에 범용 상품 선택 폼 없음) | 전체 상품을 검색/선택하는 범용 폼은 M3 범위에서 과한 UI이고, 이미 상품 상세페이지에서 자연스럽게 진입 가능하므로 중복 구현을 피함 |
| 답변 작성자에 따라 상태를 **자동으로 다르게 전이**: 티켓 소유자(구매자)가 답하면 `OPEN`(재질문), 판매자/관리자가 답하면 `ANSWERED` | 별도의 "답변 완료 처리" 버튼 없이 누가 마지막으로 말했는지만으로 "대기 중인 쪽"을 명확히 표시할 수 있음 |
| 상품질문의 공개(`isPublic`) 여부만 선택 가능, 주문문의/분쟁은 **항상 비공개** | 마스터 문서 9.4 "상품 질문(공개/비공개)"는 상품질문에만 명시된 요건이고, 주문문의/분쟁은 개인정보(배송지 등)가 섞일 수 있어 비공개가 당연한 기본값 |

## 배너/공지 CMS에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| `/admin/content`는 **배너·공지·FAQ만** 다루고, 카테고리 구조 편집은 범위 밖으로 유지 | 마스터 문서 3장 IA는 셋을 한 경로에 묶어 놓았지만, 카테고리 트리 편집은 상품/검색/필터 전반에
영향을 주는 별도 규모의 작업이라 분리. 현재는 M1 시드로 고정된 3개 카테고리(농산물/축산물/수산물)만 사용 |
| 홈 배너는 **활성 배너 중 우선순위(sortOrder) 최솟값 1건만** 노출, 캐러셀/로테이션 없음 | 광고(Ad)의 "위치당 1건만 노출" 결정과 동일한 단순화 원칙. 운영자가 여러 배너를 등록해 두고
우선순위 숫자로 교체하는 방식이 캐러셀 구현보다 훨씬 단순함 |
| FAQ는 **정적 배열 대신 DB 테이블**로 구현, `/help`와 `/admin/content`가 같은 테이블을 공유 | 분쟁 티켓 작업 때 임시로 넣었던 정적 FAQ_ITEMS 배열을 그대로 두면 운영자가 실제로 FAQ를
추가/삭제할 수 없어 "배너·카테고리·공지·FAQ"(마스터 문서 3장) 요건을 충족하지 못함 |
| 공지사항은 **홈 화면에 최신 3건만** 노출, 별도의 `/notices` 상세페이지 없음 | 마스터 문서 3장 IA 목록에 `/notices` 경로가 없고, 4.2절 홈 화면 목업도 "공지"를 홈 화면 한
섹션으로만 명시함. 개별 공지 상세보기가 필요해지면 후속 작업에서 라우트 추가 |

## 대리등록에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 대리등록 상품은 **판매자의 입점 승인 상태와 무관하게 항상 DRAFT로 생성**, 별도의 관리자
"최종 승인" 단계를 거쳐야만 ON_SALE로 전환 | 마스터 문서 10.3 "판매자 승인 없이 무단으로
농가의... 상품을 게시하지 않는다"를 문자 그대로 강제. 이미 승인된 농가라도 운영자가 대신
작성한 정보는 한 번 더 확인받아야 함 |
| 동의 확인은 **체크박스 + 출처 텍스트 입력을 관리자가 직접 작성**하는 방식(전화/문자 등
실제 동의 수단에 대한 전자 서명·녹취 연동은 없음) | 로컬 샌드박스 단계에서 실제 농가 전자
동의 시스템(SMS 인증 등)을 구축하는 것은 범위 밖. "동의 시각·출처·작업자 보존"이라는
문서 요건의 최소 구현으로 기록용 필드만 둠 |
| "농가가 수정/판매중단을 요청할 수 있게" 요건은 **판매중단/재개를 농가가 즉시 직접 처리**하는
것으로 구현(승인 대기열 없음), 상품명/가격 등 텍스트 수정은 **여전히 범위 밖**(기존 M1~M3에서
"다음 단계 예정"으로 남겨둔 상태 그대로 유지) | 판매중단은 되돌리기 쉬운 단순 토글이라 즉시
자가 처리가 안전하지만, 텍스트 필드 수정은 이미 더 큰 별도 작업(블록 에디터 포함)으로
문서화되어 있어 이번 작업에 끼워넣지 않음 |
| 대리등록 대상 판매자는 **입점 신청 여부와 무관하게 전체 판매자 목록에서 선택** 가능 | 마스터
문서 10.2는 "농업/어업경영체 등록 증빙만 있는 생산자"도 "계정/심사/상품초안 가능"이라고
명시 — 아직 미승인인 농가도 상품 초안(DRAFT)을 미리 준비해 둘 수 있어야 함 |
