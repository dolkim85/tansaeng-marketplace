# PRODUCT DECISIONS — 탄생 마켓플레이스

> 마스터 명세서(`TANSAENG_MARKETPLACE_CLAUDE_CODE_MASTER.md`) 1.3/20장 기준으로,
> M0 구현 과정에서 실제로 선택한 기본값과 그 이유를 기록한다. 법적/세무/계약 판단은 포함하지 않는다.

## 확정 사항 (마스터 문서 그대로 적용)

- 브랜드명 "탄생 / TANSAENG", 웹+PWA, 로컬 선개발.
- 기존 환경제어·운영 홈페이지와 완전 분리.
- 직접판매형(`DIRECT_SALE_ENABLED`) 기본 `false`.
- 실PG/실SMS/실카카오/실푸시 전부 Mock, 기본 비활성.

## M0에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| Next.js 16(App Router) + Tailwind CSS 4 + TypeScript strict 채택 | 마스터 문서 12.1 권장안과 일치, 생성 시점 기준 안정 최신 버전 |
| `next.config.ts`의 `cacheComponents`/`partialPrefetching` 비활성화 | 이 신규 버전의 기본 템플릿이 활성화하는 실험적 정적 우선 캐싱 모델이 `usePathname()` 등 런타임 훅과 충돌해 빌드 실패 발생. 마켓플레이스는 장바구니·주문·관리자 등 대부분 사용자별 동적 렌더링이 필요해 M0에서는 끄는 것이 안전. M1 이후 SEO가 중요한 공개 상품/카테고리 목록에 한해 `"use cache"`와 함께 선택적 재도입 검토 |
| IA(정보구조) 라우트를 공용 `PlaceholderSection` 컴포넌트로 일괄 생성 | 40개 이상의 라우트 뼈대를 각각 손으로 작성하면 중복이 커짐. 실제 기능은 M1부터 개별 구현 |
| M0 단계에서 실제 PostgreSQL/Prisma 연결 보류 | 마스터 문서 17장 M0 범위는 "안전한 프로젝트 기반"이며 DB/스토리지는 M1에서 본격 도입. 이 머신에 PostgreSQL이 아직 설치되어 있지 않아(§SAFETY_BASELINE §3) 설치 여부를 M1 착수 시 사용자에게 먼저 확인 |
| `node_modules`를 프로젝트 폴더(Windows 드라이브, `/mnt/d/...`)에 두지 않고 로컬 검증은 별도 네이티브 경로에서 수행 | WSL에서 Windows 드라이브(drvfs)로 수만 개의 작은 파일을 쓰는 `npm install`이 비정상적으로 느림(실측: 네이티브 8~9초 vs drvfs에서 10분 이상 진행 중 중단). `node_modules`는 원래 Git에도 커밋되지 않는 산출물이므로, 실제 개발 시 Windows 네이티브 Node 또는 WSL 네이티브 경로에서 `npm install`을 직접 실행하도록 README에 안내 |

## M1에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| DB를 사용자 선택에 따라 **SQLite로 우선 구현** (M2 진입 전 PostgreSQL 전환 예정) | 로컬 PostgreSQL 설치에 `sudo` 비밀번호가 필요해 에이전트가 직접 실행할 수 없었음. 사용자에게 (1)SQLite 우선 (2)직접 sudo 실행 (3)Docker 활성화 중 선택지를 제시했고 SQLite를 선택받음 |
| NextAuth(Auth.js) 대신 **커스텀 세션(bcryptjs+jose+httpOnly 쿠키)** 채택 | 이 프로젝트는 Next.js 16(매우 최신, 베타 성격의 Cache Components 등 포함)을 사용 중이라 NextAuth v5(beta)와의 호환성 리스크가 있다고 판단. 표준 OWASP 권장 요소(단방향 해시, 서명된 세션, HttpOnly/SameSite 쿠키)는 그대로 충족 |
| `next.config.ts`의 `cacheComponents`/`partialPrefetching` 비활성 유지(M0 결정 유지) | M1에서도 로그인 세션·장바구니 등 사용자별 동적 렌더링이 대부분이라 여전히 불필요 |
| `middleware.ts` → **`proxy.ts`로 전환** | Next.js 16.4.1 빌드 시 "middleware 컨벤션은 deprecated, proxy로 이름 변경됨" 경고 발생. 공식 마이그레이션 가이드대로 파일명/함수명만 변경(`middleware` → `proxy`), 동작은 동일 |
| `next dev`/`next start`에 **`-H 127.0.0.1` 명시** | `-H` 생략 시 Node 기본 동작으로 `0.0.0.0`(모든 인터페이스)에 바인딩됨을 실측으로 발견(`docs/SAFETY_BASELINE.md` §6-A). 안전기준 위반 가능성을 코드로 고정해 방지 |
| 판매자 승인 전 상품은 `DRAFT`, 승인 후 상품은 `ON_SALE`로 자동 분기 | 마스터 문서 2장의 "판매자(심사대기): 판매 게시 불가, 초안 가능" 요건을 코드로 구현. 승인 시점에 기존 DRAFT 상품도 일괄 `ON_SALE`로 전환 |
| 상품 사진/영상 업로드는 **M1 범위에서 제외** | M1 체크리스트가 넓어 핵심 거래 흐름(인증/카테고리/찜/입점심사)을 먼저 완성하고 검증하는 것을 우선함. 상세페이지는 "사진 없음" 플레이스홀더로 정직하게 표시 |
| `vitest`를 `^3`→`^4`로 업그레이드 | `npm audit`에서 `tinypool`의 치명적(critical) 프로토타입 오염 취약점 발견, 비파괴적 해결책이 메이저 업그레이드뿐이었음. 테스트 전용 devDependency라 런타임 영향 없음 확인 후 적용 |
| `eslint-config-next`의 `fast-glob` 체인, `prisma`의 `deepmerge-ts` 고위험 취약점은 **수용(accept)** | 둘 다 빌드/린트 전용 도구 체인이며 공개 인터넷에 노출되지 않는 로컬 개발 환경 한정. 수정하려면 Next 버전과 안 맞는 `eslint-config-next@14`로 강제 다운그레이드해야 해서 더 큰 위험(버전 불일치)을 감수해야 함 |

| 결정 | 이유 |
|---|---|
| 배송지는 Order에 **스냅샷 필드**(recipientName/Phone/addressLine)로 저장, 별도 재사용 가능한 Address 테이블 없음 | M2 범위를 핵심 거래 흐름(장바구니→주문→Mock결제)에 집중하기 위한 의도적 단순화. 배송지 북마크/기본 배송지 관리는 후속 단계 |

| 주문 취소 시 Payment 상태: 결제 전이었으면 `FAILED`, 결제 확인 후였으면 `REFUNDED` | 실제 환불 프로세스(PG 연동) 없이도 상태 이력을 의미있게 구분하기 위함 |

## M2 공동구매에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 별도 스케줄러/크론 없이, 화면 표시 단계(티저/오픈/마감)를 **요청마다 현재 시각으로 계산** | "초기엔 과도한 인프라 도입 지양"(마스터 문서 12.1) 원칙. 실제 DB 상태 전이(성사/미성사)는 관리자의 수동 "마감 처리" 액션으로만 일어나며, 이는 실서비스에서도 정산 담당자가 확인 후 확정하는 흐름과 자연스럽게 맞음 |
| 공동구매 참여는 **기존 장바구니/체크아웃과 별개의 간편 참여 플로우**(수량만 입력 → 즉시 주문 생성) | 공동구매는 보통 단일 상품 집중 구매라 장바구니에 섞기보다 독립 플로우가 실제 서비스 UX에도 더 가깝고 구현도 단순함. 배송지는 임시값으로 생성되고(M2 샌드박스 단순화), 추후 체크아웃 단계 합류 여부는 M3에서 재검토 |
| 가격 단계(tiers, "0~N 미성사/N 이상 1단계")는 **미구현**, 단일 확정가만 지원 | 마스터 문서 7.2가 이를 "선택" 사항으로 명시. 상태기계/환불/동시성처럼 필수 요건을 먼저 안정화하는 것을 우선함 |
| 목표 달성 집계는 **Payment.status=CONFIRMED인 주문만** 카운트, maxQty 초과 방지는 **취소 안 된 모든 주문**(결제대기+완료) 기준 | 마스터 문서 7.2 "실제 유효 결제 주문 수량"을 그대로 따름. 다만 초과판매 방지는 결제 대기 중에도 자리를 잠가야 하므로 더 넓은 기준(committedQty)을 사용 — 두 기준을 분리한 것이 핵심 설계 포인트 |
| 공동구매 재고는 **Product.stockQty와 별도**(maxQty로 독립 관리), 일반구매 재고를 차감하지 않음 | 공동구매와 일반판매가 같은 상품의 서로 다른 "채널"로 동시에 존재할 수 있다고 가정(마스터 문서 7.1 "출하예정은 공동구매 없이 일반판매 오픈 예정 상품에도 적용 가능"과 일관) |

## 상품 미디어 업로드에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 별도 객체 스토리지(MinIO 등) 대신 **Next.js `/public/uploads/` 로컬 정적 서빙** | 로컬 개발 단계에서 가장 단순하고 즉시 동작하는 방식. `docs/ARCHITECTURE.md` 외부 서비스 경계표에 전환 계획 기록 |
| 확장자/Content-Type이 아니라 **파일 앞부분 바이트(매직 넘버)로 실제 포맷 판별** | 클라이언트가 보내는 확장자/MIME 타입은 조작 가능. HTML/SVG를 위장해 올리는 것을 `src/server/media/validate.ts`가 원천 차단(마스터 문서 8.1 요건) |
| 업로드된 사진은 **무조건 `sharp`로 재인코딩**(리사이즈+JPEG 변환), 원본 그대로 저장하지 않음 | 재인코딩 과정에서 EXIF 등 메타데이터가 자동으로 제거됨(`withMetadata()`를 호출하지 않으면 sharp 기본 동작). 별도의 "메타데이터 제거" 단계를 만들 필요가 없어짐 |
| 영상은 재인코딩하지 않고 매직바이트 검증 후 그대로 저장, 60초 길이 제한은 **미검증** | 영상 길이 확인에는 ffprobe 등 추가 바이너리가 필요해 범위를 넘어선다고 판단. 용량 제한(80MB)으로만 1차 방어 |

## 배송상태/리뷰/PWA에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| Suborder 상태는 **판매자가 한 단계씩 전진만 가능**(역행·건너뛰기 불가), 결제(`Order.status=PAID`) 전에는 전이 버튼 자체를 노출하지 않음 | 상태 일관성을 단순한 코드로 보장. 송장번호 입력 등 실제 배송 연동은 범위 밖이므로 상태 라벨만으로 충분하다고 판단 |
| 리뷰 작성 자격은 **Suborder.status=COMPLETED**(배송완료)로 한정, `Order.status=PAID`만으로는 부족 | 마스터 문서 9.4 "실제 구매 완료 주문과 연결"을 엄격히 해석. 결제만 하고 아직 받지 않은 상품에 리뷰를 못 쓰게 막음 |
| 서비스 워커는 **페이지 이동(navigate) 요청의 오프라인 폴백만** 담당, API/정적자산/개인화 데이터는 전혀 가로채지 않음 | 마스터 문서 15.1 "로그인, 개인주문, 결제, 관리자... 캐싱 금지" 요건을 가장 보수적으로 만족. Turbopack 개발 서버의 HMR과 충돌할 위험도 최소화 |
| PWA 아이콘은 텍스트 없는 **추상 도형**(원+잎 모양)으로 생성 | 이 샌드박스 환경에 한글(CJK) 폰트가 없어 SVG에 한글 텍스트를 넣으면 래스터화 시 깨짐을 사전 확인(M0 스크린샷 검증 때와 동일 이슈). 실제 로고/브랜드 아이콘으로 교체는 추후 디자인 확정 후 진행 |

## 광고(Ads)에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 광고는 **위치(placement)당 1건만 선별 노출**(여러 활성 광고 중 최신 1건), 별도 경매/입찰 로직 없음 | M3 범위에서는 "광고임을 명확히 표시"가 핵심 요건(마스터 문서 11장)이고, 복수 슬롯 로테이션/경매는 과도한 범위. 최신 승인 광고 1건만 보여주는 가장 단순한 구현 선택 |
| 검색 스폰서 광고는 **검색어와 무관하게** 노출(질의-상품 매칭 없음) | 완전한 광고 랭킹 엔진은 범위 밖. 다만 "광고" 라벨은 항상 명확히 표시해 검색 품질을 왜곡한다는 오해를 방지 |
| 광고 노출수(impressions)는 **활성 광고를 실제로 조회할 때마다** 서버에서 1 증가 | 클라이언트 측 트래킹 스크립트 없이 서버 렌더링 시점에 정확히 1회 집계. 모의 지표라 완벽한 유니크 방문자 집계는 아님을 문서에 명시 |
| 광고 클릭은 **별도 Route Handler**(`/api/ads/[id]/click`)로 리다이렉트 방식 집계 | 서버 액션은 `<form>` 기반이라 단순 링크 클릭에는 적합하지 않음. GET 리다이렉트가 표준적인 광고 클릭 추적 패턴 |

## 문의/분쟁 티켓(Support Ticket)에서 추가로 결정한 사항

| 결정 | 이유 |

로직을 중복 구현하지 않고 재사용. 블록 저장 시 해당 mediaId가 **그 상품 소유**이고
**종류(이미지/영상)가 일치**하는지 반드시 재검증해 다른 상품/판매자의 미디어를 끌어오지
못하게 막음 |
| 드래그 앤 드롭 대신 **위/아래 버튼으로 순서 변경** | 새 드래그 라이브러리 도입 없이
`sortOrder` 교환만으로 구현 가능한 가장 단순한 방법. "순서 변경"이라는 요건 자체는
충족하면서 범위를 최소화 |
| 표(TABLE)·FAQ 블록은 **동적 행 추가 UI 대신 줄바꿈+구분자 텍스트 입력**(표는 `|`,
FAQ는 `Q: .../A: ...`)으로 입력받아 서버에서 파싱 | 행을 추가/삭제하는 동적 폼 상태 관리를
클라이언트에 구현하는 대신, 텍스트 파싱으로 같은 결과를 훨씬 단순하게 얻음. 파싱 함수는
순수 함수로 분리해 유닛 테스트로 형식 검증 |
| 블록이 1개 이상 있으면 **기존 `Product.description` 텍스트 필드를 대체**(둘 다 보여주지
않음), 블록이 없으면 기존 방식 그대로 폴백 | 두 콘텐츠를 동시에 보여주면 중복/혼란스러운
상세페이지가 됨. 기존 시드 상품처럼 아직 블록으로 전환하지 않은 상품은 자연스럽게 계속
동작해야 하므로 완전 교체가 아닌 폴백 방식 채택 |
| 블록 **수정(edit)은 미구현**, 삭제 후 재생성으로만 내용을 바꿀 수 있음 | 배너/공지/FAQ
CMS에서 이미 채택한 "생성/삭제만 지원" 단순화 원칙과 동일하게 적용 |

## PostgreSQL 전환에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 초기 마이그레이션은 `prisma migrate diff --from-empty`로 **실DB 연결 없이** 생성 | 작업
세션의 샌드박스에 PostgreSQL이 설치되어 있지 않고(sudo 비밀번호/Docker WSL 통합 모두 불가),
설치는 사용자가 별도 터미널에서 직접 수행해야 함. `migrate diff`는 스키마→SQL 변환만
수행하므로 DB가 없어도 마이그레이션 파일을 미리 만들어 둘 수 있어, "DB가 생기면 바로
`migrate deploy`만 실행"하는 상태로 준비해 둠 |
| `.env.example`의 `DATABASE_URL`에 **평문 예시 자격증명**(`tansaeng_dev`/`tansaeng_dev_local_only`)을
그대로 적음 | 로컬 전용 PostgreSQL 역할이며 실제 운영 비밀값이 아님. 매번 사용자가 직접
문자열을 만들어야 하는 번거로움보다, 복붙 가능한 로컬 전용 기본값을 주는 것이 M0~M3에서
이미 써온 "데모 계정 비밀번호 demo1234" 같은 관례와 일관됨(실제 운영 전환 시 반드시
교체해야 함을 ERD.md에 명시) |
| PostgreSQL 포트는 프로젝트 컨벤션대로 **55432**(기본 5432가 아님)로 고정 | `docs/SAFETY_BASELINE.md`
M0 단계에서 이미 포트 충돌 검사를 마치고 확정해 둔 값. 기존 운영 환경(스마트팜 등)과
포트를 공유하지 않기 위한 안전장치를 그대로 유지 |

## 카테고리별 판매 허가에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 입점 승인과 **완전히 분리된 별도 권한**으로 구현(입점 승인되어도 카테고리 허가는 0건부터
시작) | 마스터 문서 10.2절 5번이 입점 심사 7단계 중 하나로 "품목별 판매 가능 카테고리...
부여"를 별도로 명시. 입점 승인 시 모든 카테고리를 자동으로 열어주면 이 요건을 무력화함 |
| 축산물/수산물(seafood)은 UI에 **"추가 허가/신고/표시·이력관리 대상" 안내 문구만** 표시,
실제 서류 업로드·인증 확인 로직은 구현하지 않음 | 마스터 문서 10.1절이 요구하는 것은
실제 축산물 HACCP 인증 등 전문 검증 체계인데, 이를 로컬 샌드박스에서 흉내 내는 것은
의미가 없다고 판단. 관리자가 수동으로 판단해 승인/반려하는 것으로 충분 |
| **대리등록 상품(`createProxyProductAction`)은 이 검증에서 제외** | 대리등록은 이미
관리자가 직접 생성하고 별도의 "최종 승인" 단계(`approveProxyProductAction`)를 거치는
흐름이라, 카테고리 허가까지 추가로 요구하면 같은 관리자 승인을 두 번 요구하는 중복이 됨.
관리자가 이미 전적으로 책임지고 생성하는 경로이므로 예외로 둠 |
| 반려된 요청은 **재요청 시 PENDING으로 되돌림**(별도의 "재요청" 레코드를 새로 만들지 않고
upsert) | 판매자 입점 신청의 재신청 패턴(이력을 남기려고 새 레코드 생성)과는 다르게,
카테고리 허가는 `(sellerId, categoryId)` 복합 유니크 제약이 있어 애초에 레코드가 1개만
존재할 수 있음. 이력 보존보다 단순함을 우선 |
| 서버 액션(`createProductAction`) 내부에서 **직접 허가 상태를 재조회**해 검증 — 클라이언트의
카테고리 선택지 필터링에만 의존하지 않음 | UI 필터는 사용자 편의일 뿐 보안 경계가 아님.
실제로 승인되지 않은 카테고리 id를 강제로 제출하는 공격을 E2E로 재현해 서버가 올바르게
거부하는지 확인함 |

## 접근성/SEO/보안/동시성 점검에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 동시성 보호는 **단일 행 원자적 조건부 업데이트**(가능한 경우) 또는 **`SELECT ... FOR UPDATE`
행 잠금**(여러 행의 합계를 다시 계산해야 하는 경우)로 구현, SERIALIZABLE 격리수준 전환은
사용하지 않음 | 일반 결제/주문취소는 단일 `Product`/`Order` 행의 조건부 `updateMany`
(`WHERE ... AND stockQty >= quantity`)로 충분히 원자적이라 가장 단순한 방법을 선택.
공동구매 참여는 여러 `OrderItem`의 합계를 다시 계산해야 해서 같은 트릭을 쓸 수 없어,
해당 `GroupBuy` 행만 잠그는 `FOR UPDATE`를 사용(다른 공동구매의 참여는 막지 않음).
SERIALIZABLE 전환은 재시도 로직까지 필요해 범위를 넘어선다고 판단 |
| 발견한 동시성 버그 4건은 **실제 동시 HTTP 요청으로 재현 후 수정**(코드 추론만으로 끝내지
않음) | "대량주문·동시성 테스트"라는 요건의 본래 의도가 실제 경쟁 상태를 잡아내는 것이므로,
Playwright로 여러 브라우저 컨텍스트를 동시에 실행해 재현했다. 그 결과 일반 결제 재고
차감, 주문취소 중복복구, 정산 배치 중복집계까지 — 공동구매 외에도 같은 패턴의 버그가
더 있었음을 확인 |
| 체크아웃/공동구매 참여의 **사전 재고 확인은 그대로 유지**(트랜잭션 밖, UX용), 트랜잭션
내부의 원자적 재검증을 **추가**로 둠(이중 방어) | 사전 확인이 없으면 흔한 "이미 품절"
케이스에서도 트랜잭션을 열었다가 롤백해야 해서 비효율적. 사전 확인은 좋은 UX(구체적 상품명
표시)를, 트랜잭션 내부 재검증은 진짜 안전성을 담당하도록 역할을 분리 |
| Content-Security-Policy 헤더는 **보류**, 그 외 기본 헤더(X-Content-Type-Options/
X-Frame-Options/Referrer-Policy/Permissions-Policy)만 적용 | CSP를 정확히 설정하려면 Next
dev 모드의 HMR/eval, Google Fonts 등 실제 운영 도메인이 확정된 뒤에나 정할 수 있는 소스
목록이 필요함. 이미 `dangerouslySetInnerHTML`을 전혀 쓰지 않아 XSS는 React 자체 이스케이프로
방어되므로, CSP는 운영 배포 직전 추가해도 늦지 않다고 판단 |
| SEO 메타데이터는 **상품/카테고리/농장 스토어 3개 공개 페이지에만** `generateMetadata` 추가,
나머지 페이지는 루트 레이아웃의 기본 제목 그대로 유지 | 이 세 페이지가 검색엔진이 실제로
색인할 가치가 있는 "콘텐츠 랜딩 페이지"이고, 그 외 페이지는 대부분 로그인 필요 개인화
화면이거나 목록 성격이라 추가 메타데이터의 가치가 낮음(과도한 범위 확장 지양) |
| `robots.ts`/`sitemap.ts`의 도메인은 **로컬 URL을 그대로 사용**, 실제 배포 도메인 확정 전까지
placeholder로 유지 | 마스터 문서 20장이 이미 "실제 도메인 미확정"을 명시. 이 값이 틀려도
로컬 개발에는 영향이 없고, 실제 배포 시점에 한 줄만 바꾸면 되므로 지금 새 환경변수를
만드는 것은 과한 선행 설계 |
| 상품 상세 블록 에디터의 이미지/영상에 **대체텍스트(alt) 입력란을 추가**(선택 입력,
기본값 빈 문자열) | 블록 에디터 작업 때는 발견하지 못했던 간극 — 상품 설명에 들어가는
이미지는 인접한 설명 텍스트가 없어 대체텍스트 없이는 화면낭독기 사용자가 내용을 전혀 알 수
없음. 목록/카드형 이미지(제목이 바로 옆에 보이는 경우)는 의도적으로 `alt=""`를 유지해
중복 안내를 피함(WCAG의 "중복 텍스트 대안" 권고와 일치) |

## 상품 기본정보 수정에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| **slug는 제목이 바뀌어도 절대 바꾸지 않음**(새 slug 재생성 없음) | 공개 상품 URL이 이미
`sitemap.xml`에 등록되고 검색엔진에 색인될 수 있는 상태라, 제목 수정 때마다 URL이
바뀌면 기존 링크가 모두 깨지고 SEO 신호도 손실됨. "제목 변경"과 "URL 식별자"는 분리된
개념으로 취급 |
| 기본정보 수정은 `createProductAction`과 **동일한 필드셋**(상품명/카테고리/가격/재고/
원산지/설명)을 다룸, 카테고리를 바꾸는 경우 생성 때와 동일하게 APPROVED 판매 허가를
재검증 | 사용자가 "제목/가격/원산지"만 요청했지만, 편집 페이지의 기존 TODO 문구가
"등 기본 정보"로 더 넓게 명시했었고 신규등록 폼의 필드와 불일치하는 반쪽짜리 수정
폼을 만들 이유가 없어 전체 필드를 동일하게 제공. 카테고리 허가 검증을 생성 때와
별개 경로로 두면 보안 구멍이 생기므로 동일한 검증을 재사용 |
| 재고 수정 시 **별도의 "판매중단/재개" 상태와 충돌하지 않도록 status는 건드리지 않음** |
`stopSellingProductAction`/`resumeSellingProductAction`이 이미 ON_SALE↔HIDDEN 전환을
담당하므로, 기본정보 수정 폼은 수량만 바꾸고 판매 상태 전환은 그대로 별도 버튼의 책임으로
남김(관심사 분리) |
| 상세 설명(description)도 편집 가능하게 유지했지만, **블록이 1개 이상이면 공개 페이지에는
여전히 노출되지 않음**을 폼에 안내 문구로 명시 | 이미 블록 에디터 작업에서 "블록이 있으면
description 대신 블록을 렌더링"으로 결정했음(ERD.md 참고). 사용자가 description을 수정해도
블록이 있으면 반영되지 않는다는 점을 혼동하지 않도록 폼에서 바로 안내 |

## 관리자 카테고리 트리 관리 UI에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| **트리 깊이를 최상위-하위 2단계로 강제**(상위로 지정 가능한 카테고리는 `parentId === null`인
카테고리로만 제한) | `getCategoryWithProducts`(카테고리 상세) 등 기존 조회 로직 전체가
"최상위 카테고리 + 그 직계 자식들"만 가정하고 작성되어 있어서, 3단계 이상을 허용하면
그 로직들이 조용히 틀린 결과를 반환하게 됨. UI와 서버 액션 양쪽에서 이 제약을 강제 |
| **slug는 생성 후 변경 불가**(이름은 변경 가능) | 상품/카테고리 모두에 적용한 동일한 원칙
(PRODUCT_DECISIONS.md의 "상품 기본정보 수정" 절 참고) — 공개 카테고리 URL이 이미
`sitemap.xml`에 등록되어 있을 수 있어 slug가 바뀌면 기존 링크가 깨짐 |
| 삭제는 **하위 카테고리나 연결된 상품이 하나라도 있으면 거부**, UI에서도 그 조건이면
삭제 버튼 자체를 "삭제 불가(...)" 안내로 대체 | 판매 중인 상품의 카테고리가 관리자의
클릭 한 번으로 갑자기 사라지는 사고를 막기 위함. 서버 액션에서도 동일한 조건을 재검증해,
UI를 우회해 폼을 직접 제출하는 경로까지 방어 |
| 하위 카테고리에 연결된 `SellerCategoryPermission`은 카테고리 삭제 시 **자동으로 함께
삭제**(기존 스키마의 `onDelete: Cascade` 그대로 활용) — 단, 삭제 자체가 상품/하위카테고리
존재 시 거부되므로 실제로는 "요청만 있고 실제 상품은 없는" 카테고리를 삭제할 때만 발생 |
기존 `SellerCategoryPermission.category` 관계가 이미 `onDelete: Cascade`로 설계되어 있어
별도 처리 없이 일관되게 동작. 상품이 있는 카테고리는 애초에 삭제 자체가 막히므로 이
cascade가 실수로 큰 범위의 데이터를 지우는 일은 없음 |

## 판매자 스토어 소개·정책에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| 스토어 이름(`storeName`)은 **이 화면에서 수정 대상이 아님**, 소개/배송정책/반품정책 3개
필드만 다룸 | 마스터 문서 3장 라우트 설명이 "/seller/store 생산자 스토어 **소개·정책**"으로
명확히 범위를 한정함. 이름 변경은 요청받지 않은 범위라 추가하지 않음(필요해지면 별도
작업으로 분리) |
| 반품 정책만 **상품 상세페이지에도 중복 노출**, 소개/배송정책은 스토어 페이지에만 노출 |
마스터 문서 4.4절 6번 "구조화 정보"가 상품 상세페이지 항목으로 "반품 정책"을 명시적으로
나열함. 나머지 두 필드까지 상품 페이지에 전부 반복하면 정보가 과하게 중복되어 오히려
가독성을 해침 |
| 세 필드 모두 **선택 입력**(필수 아님), 비우면 저장 시 `null`로 변환되어 공개 페이지에서
해당 섹션 자체가 사라짐(빈 제목만 있는 섹션 노출 방지) | 아직 소개/정책을 작성하지 않은
신규 판매자의 스토어 페이지가 빈 섹션 제목들로 어색해지는 것을 방지. "값이 없으면 섹션
자체를 숨긴다"는 패턴은 이미 FAQ/공지 등 다른 CMS 기능에서도 일관되게 사용 중 |

## 관리자 운영설정(/admin/settings)에서 추가로 결정한 사항

| 결정 | 이유 |
|---|---|
| **실결제/실발송 관련 플래그(DIRECT_SALE_ENABLED, PAYMENT_PROVIDER, NOTIFICATION_PROVIDER)는
이 화면에서 "읽기 전용"으로만 표시**, 절대 수정 가능한 UI 토글로 만들지 않음 | 이 값들을
웹 UI에서 즉시 바꿀 수 있게 하면, 관리자 계정이 탈취되거나 실수로 클릭 한 번에 실결제가
켜지는 사고가 날 수 있음. `docs/RELEASE_CHECKLIST.md`가 "실결제, 실발송... 전부 사용자
사전 승인 필요"라고 명시한 것과 "웹 UI 토글 가능"은 정면으로 충돌함. 환경변수를 통한
배포 단계 변경만 허용 |
| 중개수수료율은 **전역 상수(`COMMISSION_RATE`)에서 DB 싱글톤(`PlatformSettings`)으로
전환**, 관리자가 UI에서 직접 변경 가능 | 마스터 문서 11.1절이 "구체 수수료율은 관리자
설정"이라고 명확히 요구함(실결제 플래그와 달리 이것은 명시적으로 "확정"된 요구사항).
금액에 직접 영향을 주지만 결제 자체를 켜고 끄는 위험과는 성격이 다름 |
| 수수료율 변경은 **다음 정산 배치부터만 적용**, 과거 `Settlement` 레코드의
`commissionRate`는 생성 시점 값을 스냅샷으로 보존해 바뀌지 않음 | 이미 승인(지급완료)된
정산 배치의 금액이 나중에 수수료율을 바꿨다고 소급 변경되면 회계적으로 심각한 문제가 됨.
실제로 동시성 테스트와 유사한 방식으로 "수수료율 변경 후 새 배치 생성 → DB에서
commissionRate 스냅샷 값 확인"을 재현해 검증함 |
| 약관 버전은 **생성만 가능, 수정·삭제 불가**(다른 CMS류 모델의 "생성/삭제만" 패턴과도
다른 예외) | 법적 성격의 버전 이력은 과거 버전이 조작된 것처럼 보이면 안 됨. 실수로
잘못 등록한 경우에도 새 버전을 다시 등록하는 방식으로 정정하도록 유도(이력에 "정정"
흔적이 남는 것이 오히려 투명성 측면에서 더 올바름) |
| 구매자 동의 기록·법적 효력 연동은 **범위 밖으로 유지** | 마스터 문서 16장(사전 출시
법적 체크리스트)이 "이용약관 버전 동의 기록"을 **실제 출시 전 법무 검토 대상**으로 따로
분류해 두었음. 지금 구현하는 것은 버전 이력을 "보존"하는 것뿐이고, 실제 사용자 동의를
법적으로 유효하게 기록하는 메커니즘은 전문 법무 검토 후 별도로 설계해야 함 |
